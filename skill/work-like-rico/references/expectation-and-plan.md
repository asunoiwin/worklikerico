# 预期检查与可下发方案

项目型任务，或目标、对象、执行口径、完成条件仍模糊时，使用本参考。事实问答、机械转换和目标明确的单步可逆操作不需要套用；用几句话说清结果和检查方式后直接执行。

## 先用已有材料补齐

先读当前请求、已确认版本或样例、现有产物、运行事实、历史纠正与已知边界，形成助手自己的第一版判断。只有缺失内容会改变目标、范围、不可逆操作或最终验收，而且无法从现有材料可靠判断时，才集中提出必要问题。不要把下面的检查项逐条变成问卷，也不要用等待用户回答代替可继续的调查和准备。

当前明确要求优先于历史记录。历史材料用于发现满意结果、返工原因和推进方式，不扩大授权，也不把私人业务细节写入通用规则。

## 六项预期检查

1. **目标成立。** 要解决的实际问题是什么，完成后哪个现实状态应发生变化？先核对业务理由；不要从准备采用的工具、安装方式或技术分支反推目标。
2. **结果对齐。** 使用者最终要拿到、使用或确认什么？列清最终对象、已确认样例或版本、必须保留的内容。安装成功、文件数量、命令退出或分支 PASS 只能证明相应动作。
3. **范围完整。** 明确本阶段对象全集、每类需要检查的字段、相关收尾和明确后置项。对象应可逐项定位；既不遗漏剩余对象，也不把未来愿景并入当前交付。
4. **前提可用。** 核实现状、输入、资源、权限、数据和外部依赖；把事实、假设、未知分开。计划中的供给、未经选择的方案和来源自述不能当成当前能力。
5. **完成可判断。** 实施前说明检查哪个实际对象、按什么口径、用什么证据判断。区分执行者声明、独立证据和用户认可；检查字段、统计范围、时间口径和异常处理必须没有多种解释。
6. **取舍可解释。** 方案规模、验证强度和协作方式与影响相称。授权内可逆判断由助手承担；只有影响目标或越过不可逆边界的必要选择才交给用户。清晰小操作不升级为项目流程。

六项不要求写成固定表格。复杂任务逐项保留判断，简单任务压缩成几句话；压缩的是呈现，不是对象范围或完成证据。

## 写成可直接执行的方案

方案要让执行者无需猜测即可行动，至少交代：

- **结果：** 最终要出现的用户可用状态，不用工具动作代称结果。
- **范围：** 具体对象全集、每个对象要处理或检查的字段，以及排除和后置事项。
- **输入：** 来源、已确认版本、必须保留内容；标出事实、假设和未知。
- **顺序与依赖：** 哪些步骤可并行，哪些必须等前一步证据，哪个外部条件只阻塞哪一段。
- **owner：** 每个下一动作的负责人，以及谁负责最终集成和完成判定。
- **完成证据：** 观察哪个实际产物、服务或用户路径，证据绑定哪个版本；谁检查，何时需要独立复核或人工验收。
- **偏离处理：** 发现目标不成立、对象遗漏、依赖变化、证据不符或授权越界时，如何校准、保留成果、暂停相应边界并继续无关工作。

对象名、检查字段和执行口径要具体；“全部处理”“正常”“按需”“验证一下”不能单独作为范围或完成条件。已约定期限和用户修改要原样保留；没有约定的时间不要自行编造。

多步、委派或需跟进的工作，在预期和方案确定后，再用 [task-supervision-contract.md](task-supervision-contract.md) 记录状态、owner、证据和停止条件，不另建重复系统。

## 分支集成与结果表达

主线程按原始目标逐项验收各分支：确认它们共同覆盖了对象全集、依赖和最终用户结果。分支测试通过、报告数量或 PASS 总数不是主线进度；局部失败只影响依赖它的范围，局部成功也不能替代最终集成。

对用户的结果保持简短，先说已成事实和决定性证据，再说剩余风险或真正需要的一步。内部记录保留来源、版本、对象覆盖、检查口径和偏离处理，使简短结论仍可追溯。

用户的简短认可应按当次语境记录：认可方向、表达或某项结果，不自动等于整项交付通过。未表达的认可范围不自行扩展；持续独立执行和以后同类任务的质量仍需实际行为与结果验证。
