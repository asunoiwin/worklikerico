# 统一管理入口：最小实施约定

2026-09-09。承接用户的“一个集合，方便安装、使用、管理”，只补现有安装器之间的入口，不新增后台服务、数据库或插件加载系统。

## 原因与交付

问题在设计职责层：能力已归入一个仓库，但用户仍需区分多个安装脚本，Hermes 核心还要手工链接。统一入口负责选择平台和模块、显示操作、顺序调用既有安装器；各安装器继续负责自身安装状态。

交付为 `python3 scripts/manage.py`，保留原脚本兼容。技能正文仍按平台原生方式按需读取，不把全量技能内容组合成常驻提示词。

## 命令约定

- `list [--platform codex|claude|agents|hermes]`：显示可用能力的名称、类型、平台、简短介绍；读取现有 catalog 与声明，不输出技能正文。
- `install --platform ... [--skill NAME ...] [--plugin NAME ...] [--home PATH] [--dry-run]`：无模块筛选时安装该平台已声明兼容的集合；有任一模块筛选时仅安装明确选中的模块。名称在列表中可直接找到，重复选择去重。
- `update --platform ...`：先检查工作区干净，再 `git pull --ff-only`，成功后按同样选择安装新版本。支持与 install 相同的模块选择、临时 home 与 dry-run。失败返回非零，明确源代码同步和安装分别完成到哪一步。
- 所有未知平台、模块或不兼容组合，在产生安装副作用前报错。dry-run 不执行拉取、安装、构建或目录写入，只输出计划；它不能承诺尚未拉取的远端版本内容。
- 不增加定时更新、自动卸载、删除旧仓库或权限设置。现有底层移除命令继续按原说明使用。

为支持可选模块，底层插件安装器可增加兼容的 `--plugin NAME` 筛选，默认行为保持不变。不得让“只装一个 skill”顺带安装所有插件。

Hermes 核心 `work-like-rico` 纳入已有 catalog 的 hermes target。当前只管理已明确兼容的核心与 xmind，不因此宣称其他平台的插件都能装入 Hermes。SOUL、订阅、渠道与后台服务配置继续沿用现有独立安装说明。

## 影响范围五项

| 项目 | 范围 |
|---|---|
| 入口 | 新 manage 命令；原安装命令保持可用 |
| 数据与状态 | 读取现有 catalog、平台登记；不新增持久状态或数据库 |
| 依赖 | 复用 Python、Git 及已有安装器所需环境，不增加模型调用 |
| 副作用 | 仅显式 install/update 执行对应平台安装；update 可快进源码；默认不跨平台 |
| 失败与回退 | 选择错误不改状态；子进程失败立即停止后续步骤并保留可诊断结果；不自动回滚源码或删除用户内容 |

## 同义入口检查

| 相关词/入口 | 已发现位置 | 处理 |
|---|---|---|
| install / 安装 | README、三个现有安装器 | 新入口调用原安装器，首页改为统一命令 |
| update / 更新 / pull | README 更新段、插件复制缓存 | 统一说明源码同步后重新安装；不把拉取成功当安装成功 |
| Hermes / 核心 / symlink | catalog、Hermes INSTALL | 核心通过已有技能安装器管理，替换手工链接示例 |
| remove / uninstall | 底层安装器与迁移文档 | 保持既有受管入口移除边界，不新增统一删除功能 |

## 双面影响

正向：用户按平台和目录名称管理一个集合，不再记忆脚本分工；可只装所需模块。反向：首次默认平台安装仍会安装该平台全部兼容模块，所以首页必须解释选择语义；update 只同步干净工作区，不能覆盖正在编辑的内容。规则文案随软链接更新与插件复制到缓存的差异应说清楚，不承诺旧会话自动重新加载。

## 验收

1. 列表能给出名称和简介，平台过滤正确，不加载或打印技能正文。
2. 临时 home 真实安装 Hermes 核心和 xmind；重复安装不制造副本，同名外来入口保留。
3. 仅选一个 skill 不安装插件；仅选一个插件不安装无关技能/插件；多模块选择校验完再开始执行。
4. 未知/不兼容选择、安装失败、脏工作区更新均返回非零，后续步骤不执行；dry-run 不修改目录与 Git。
5. 更新顺序与快进限制以隔离测试或受控子进程验证，不为验收修改真实 Codex/Claude 安装。
6. 原安装器适用回归通过，独立检查入口与文档一致。真实 Hermes 入口只做幂等接续核验，不重启网关、不调用模型、不恢复日常任务。
