# 结构化台账案例：从字段覆盖到可维护关系

## 案例边界

这是一次真实台账整理案例的脱敏复盘，用来校准 Work Like Rico 的预期制定方式，不是新的流程或通用硬门禁。公开内容不包含人员、实际地点、网络地址、设备标识、凭据或私有材料路径。以下记录区分早期试验、实际执行和用户后续反馈，不以技术检查代替满意度。

## 暴露出的预期缺口

首轮规划识别出一个对象可能对应多条地址和端口，但没有把稳定身份、关系基数、唯一维护位置和完整查询行为落实成可执行方案。它还为缺少正式标识的对象设计了可能重复的占位方式，并让部分信息在多个位置重复维护。该轮规划结论为 **PARTIAL**，不能直接交给执行者。

实施早期又暴露出两个问题：一是“源内容全部有去向”会掩盖内容被分到错误类别，二是模板虽然有输入字段，却没有证明新增、改名、删除后派生结果会正确更新。最终交付由主线程多次修正，不能反推首轮规划已经具备独立交付能力。

## 最小改进

对需要长期维护的结构化产物，制定预期时除字段和对象全集外，再明确三件事：

1. 对象间是一对一还是一对多，用什么稳定身份关联；缺少正式身份时不得制造会冲突的统一占位。
2. 每类人工信息只在哪一处维护，其他位置如何派生或查询，避免同一事实被重复修改。
3. 验收把“内容覆盖”“语义归类与关系正确”“真实维护动作后的结果”分开；代表性新增、修改、删除或查询至少覆盖本次承诺的关键行为。

这些要求只在产物承诺长期维护、关联查询或自动派生时适用。一次性表格、机械转换和没有关系结构的简单材料不因此增加流程。

## 已验证与未确认

早期修正候选经过逐项来源对照、身份与关系检查，以及维护动作后的实际重算；主要数据与维护行为通过独立审计。部分图形界面操作只得到有限验证。当时用户没有确认最终满意，不能记录为用户验收通过，也不能把结果归功于首轮规划。

## 后续真实执行与用户收敛（2026-09-11）

Hermes 随后实际使用用户指定原模板与原始资料生成工作簿。独立检查发现规划地址只保留原始副本而未结构化、资源表未填写、跨表位置未同步、未确认对象仍混入查询入口。接续修正又暴露出查询公式缺失、动态函数兼容及文本/数字身份比较失败。最终通过实际重算，证明修正版本的查询有效；该结果依赖外部审查和多轮具体纠偏，不证明自主规划或无人监督交付已通过。

用户随后明确要求由主线程直接优化，不再交给 Hermes。后续版本获“基本信息已经对齐”的有限认可，但用户同时指出模板组织丢失，要求恢复原来的首页、表名和清单，删除不需要的独立页。再后的指令收窄为指定对象下架、清理来源说明、删除新增资源记录和调整凭据字段顺序，最后要求按同一格式制作空白模板。这些是明确的范围及维护偏好；请求继续修改或制作模板不等于对所有既有内容的最终认可。

由此补充的预期有三点：

- 正确数据与熟悉格式分别验收。允许修正字段含义，不等于允许替换用户已选定的表名、顺序、布局或维护方式。
- 日常交付只保留完成工作需要的信息。追溯证据有内部保存价值，不自动成为用户每天维护的额外页或备注；先判断已有字段能否承载，避免因归类方便新增结构。
- 用户要求局部修改时，明确保留基线，更新直接关联并检查其余数据不变。用户明确删除的信息不再换一个位置保留在日常交付中。

主线程后续交付采用逐值差异与真实查询重算检查，覆盖用户名/密码列移动、管理与业务端口分离、空输入及无匹配输入。空白模板另清除原业务数据、凭据和历史页，并用虚构记录检验最后一行的查询。这里的执行主体是主线程，不能登记为 Hermes 行为复测通过；这些检查也没有验证今后不同任务的稳定表现。

## 另一场景的有限验证

最小参考修订后，用全虚构采购、分批收货和退货资料做了一次隔离 Hermes 原生规划。模型实际读取了本参考，约 73 秒内完成，4 次主模型调用、5 次工具调用。独立审查仅拿输入和原方案，结论仍为 **PARTIAL**：分表方向合理，但采购汇总缺失、无采购单的借样信息落点不足、来源不明补记被拼入另一记录的原因、同名供应商处理产生重复维护，收货行身份也不足以明确未来退货归属。

这一结果证明参考可发现和读取，不能证明规则能稳定改变实际决策。没有把审查答案写回原方案，也没有生成第二套业务系统。当前缺口在实际规划质量和监督纠偏闭环；不能只凭格式校验或多加指令宣布具备独立工作能力。本次没有验证默认 GPT 路线在同场景中的表现，也没有验证实际执行。
