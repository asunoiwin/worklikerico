# 结构化台账案例：从字段覆盖到可维护关系

## 案例边界

这是一次已完成的真实台账整理案例的脱敏复盘，用来校准 Work Like Rico 的预期制定方式，不是新的流程或通用硬门禁。公开内容不包含人员、实际地点、网络地址、设备标识、凭据或私有材料路径。

## 暴露出的预期缺口

首轮规划识别出一个对象可能对应多条地址和端口，但没有把稳定身份、关系基数、唯一维护位置和完整查询行为落实成可执行方案。它还为缺少正式标识的对象设计了可能重复的占位方式，并让部分信息在多个位置重复维护。该轮规划结论为 **PARTIAL**，不能直接交给执行者。

实施早期又暴露出两个问题：一是“源内容全部有去向”会掩盖内容被分到错误类别，二是模板虽然有输入字段，却没有证明新增、改名、删除后派生结果会正确更新。最终交付由主线程多次修正，不能反推首轮规划已经具备独立交付能力。

## 最小改进

对需要长期维护的结构化产物，制定预期时除字段和对象全集外，再明确三件事：

1. 对象间是一对一还是一对多，用什么稳定身份关联；缺少正式身份时不得制造会冲突的统一占位。
2. 每类人工信息只在哪一处维护，其他位置如何派生或查询，避免同一事实被重复修改。
3. 验收把“内容覆盖”“语义归类与关系正确”“真实维护动作后的结果”分开；代表性新增、修改、删除或查询至少覆盖本次承诺的关键行为。

这些要求只在产物承诺长期维护、关联查询或自动派生时适用。一次性表格、机械转换和没有关系结构的简单材料不因此增加流程。

## 已验证与未确认

修正后的候选产物经过逐项来源对照、身份与关系检查，以及维护动作后的实际重算；主要数据与维护行为通过独立审计。部分图形界面操作只得到有限验证。用户没有确认最终满意，因此本案例只能证明修正版本达到已执行检查的标准，不能记录为用户验收通过，也不能把结果归功于首轮规划。

## 另一场景的有限验证

最小参考修订后，用全虚构采购、分批收货和退货资料做了一次隔离 Hermes 原生规划。模型实际读取了本参考，约 73 秒内完成，4 次主模型调用、5 次工具调用。独立审查仅拿输入和原方案，结论仍为 **PARTIAL**：分表方向合理，但采购汇总缺失、无采购单的借样信息落点不足、来源不明补记被拼入另一记录的原因、同名供应商处理产生重复维护，收货行身份也不足以明确未来退货归属。

这一结果证明参考可发现和读取，不能证明规则能稳定改变实际决策。没有把审查答案写回原方案，也没有生成第二套业务系统。当前缺口在实际规划质量和监督纠偏闭环；不能只凭格式校验或多加指令宣布具备独立工作能力。本次没有验证默认 GPT 路线在同场景中的表现，也没有验证实际执行。
