# 满意标准、预期制定与 Hermes 能力整合任务书

2026-09-09 按用户最新说明校准。日常监测继续暂停；设计—验收插件过度触发、模型能力变化与性能的对比优化明确后置。

## 本次真正要交付什么

把已验证、长期使用的能力收进一个便于安装、升级和管理的集合，让 Hermes 按需使用，并按照 Rico 认可的结果与工作方式判断、下发和推进工作。

单一仓库、插件能安装、某个技能能执行是基础证据。最终要检查：Hermes 是否在执行前把预期定对、把方案补完整，在执行中识别偏离和真实阻塞，并以符合要求的结果收尾，减少用户反复补需求、纠偏和催进度。

历史记录研究必须回答两件事：什么结果是可接受的，以及怎样推进才符合 Rico 的要求。现有研究更多提炼了纠错规则，不能据此宣称已经完整理解满意标准。

## 如何判断预期是否正确

下面是针对项目和模糊任务的工作结构，不是每项操作必须填写的表格。小任务用几句话说清结果、边界和检查方式即可。

1. **目标成立。** 说明要解决的实际问题，以及完成后哪种状态应发生变化。先核对业务理由，不能从准备采用的工具或技术反推目标。
2. **结果对齐。** 指定使用者真正要拿到、用到或确认的结果；列清样例、用户最后确认的版本和必须保留的内容。动作、文件数量、安装成功不能替代结果。
3. **范围完整。** 明确涉及的对象全集、当前阶段、相关收尾事项，以及明确后置的工作。既不遗漏关键对象，也不把未来愿景变成当前必须完成的扩展。
4. **前提可用。** 核实现状、资源、权限、数据和外部依赖；把事实、假设、未知分别写清。不能把预计供给当现有能力，或者把未经选择的方案变成用户的新阻断。
5. **完成可判断。** 在实施前约定检查哪个实际对象、用什么证据判断结果。区分执行者声明、独立证据与用户认可；没有明确认可时，只能说满足了哪些已知条件。
6. **取舍可解释。** 方案规模、验证强度和协作方式应与影响相称。能根据已有信息自行决定的事项直接处理，只有影响目标或不可逆边界的必要选择才集中交给用户。

这些判断由助手先通过记录和现状调查完成，不变成让用户逐项回答的问卷。

## 怎样下发足够完整的方案

执行者应能看清：要实现的结果、对象和边界、输入依据、工作顺序与依赖、各自责任、完成证据，以及遇到什么情况应修正方案或交回决定。

主线程负责把各分支结果重新对照原目标，不能只汇总子任务的 PASS。局部问题不阻塞无关主线；发现执行在优化一个不再服务原目标的指标时，应重新校准任务，而不是继续扩大该分支。

已经约定的期限和用户修改要保留。未约定的时间不自行编造，材料不完整也不通过额外承诺或缩小目标掩盖。

## 按需加载与整合边界

Hermes 与 Codex 已有技能名称/简介发现、命中后读取正文的机制。统一集合优先复用原生目录和链接，不额外建立索引数据库、聚合全部技能正文的提示词或新的调度器。

Hermes 记忆优先使用它自身的独立设置和管理能力。Codex 记忆插件保留在集合内供对应平台使用；只有原生能力确有用途缺口时才考虑补充，不能把统一源码管理误解为所有平台采用相同运行实现。

常驻的 SOUL、项目规则、记忆摘要、工具说明与自动 hook，需要和按需技能正文分别看待。减少技能数量并不自动消除这些开销；本阶段只确认边界，具体性能和过重流程优化后续再做对比。

原始聊天、项目私密信息与来源定位留在本机受限目录。公开仓库保存脱敏判断规则和实现。当前直接要求优先于历史推断，历史业务消息不构成新的执行授权。
