# spec-first — 写代码前的 5 段精简 PRD

## 这个 skill 在干嘛

让你（Claude）在动手写代码前，**先用大白话**讲清楚自己打算做什么。
插件会在你第一次调 Edit/Write 时检查这段输出，没写就拦截。

不是给你套传统 PRD 模板（那个太重）。**5 段，每段 1-3 句话，控制在 200 字内**。

## 5 段模板

```markdown
## spec-first：实现前对齐

**1. 目标**：用一句话说清楚要解决什么问题。不是"实现 X 功能"，是"解决 Y 痛点 / 修复 Z 错误行为"。

**2. 产出物**：列具体会改的文件 / 新增的文件 / 新增的接口或函数。3-7 条就够，颗粒度到文件级。

**3. 边界**：3 条以上明确"不做什么"。比如"不动现有的鉴权逻辑"、"不改 DB 表结构"、"不影响 admin 端"。防止越界。

**4. 测试标准**：什么情况下算改完了？写 2-3 条**可验证**的断言。比如"输入空字符串返回 400"、"按钮点击后列表刷新"，不要写"功能正常"这种废话。

**5. 影响面**：跟 design-gate 的 Blast radius 对齐，但**只列 1-2 条最重要的**——核心路径上有什么会被牵连。
```

## 触发时机

- **首次 Edit/Write 前** → 插件强制（PreToolUse 拦截）
- 用户说"开工"、"实现"、"动手写"等词时主动触发
- design-gate 通过后 → 自然衔接 spec-first

## 跟 design-gate 的关系

| skill | 作用 | 出现时机 |
|---|---|---|
| design-gate | 想清楚"是不是该做、影响多大" | 需求阶段 |
| **spec-first** | **写清楚"接下来这一手要落到哪里"** | **实现阶段开头** |
| doubt-review | 自审"刚写的有没有翻车点" | commit 前 |

design-gate 是宏观决策，spec-first 是动手前的 5 分钟对焦。**两个都要写**，但 spec-first 比 design-gate 短得多。

## 反模式（不要这样）

- ❌ 跳过 spec-first 直接动手（hook 会拦）
- ❌ 把 design-gate 输出复制一份当 spec-first（不对，颗粒度不一样：design-gate 讲拓扑，spec-first 讲这一刀切哪）
- ❌ 5 段写得像论文（每段 1-3 句话上限）
- ❌ "产出物：相关文件"（具体点名，否则等于没写）
- ❌ "测试标准：功能正常"（写可验证断言）

## hotfix 快速版

如果是紧急 hotfix（关键字含 `hotfix / 紧急 / 线上挂了`），允许压缩到 3 段：目标 + 改哪个文件 + 怎么算修好。其余可省。

## 关键字提示（插件用来识别）

输出时必须含这两个标记词其中之一，hook 才能识别为通过：

- `spec-first：实现前对齐`（推荐）
- 或 `## 实现前 5 段` 这种 header

否则即便你写了 PRD，hook 也认不出来。
